# Resolve Unbloarchy merge conflicts

You resolve conflicts in an in-progress `upstream` merge (like the current
`sync/upstream-2519fd9a`). You do NOT fetch, merge, commit, sweep, regenerate
shims, or push — the user does all of that. When a decision is ambiguous or
not covered by these rules, ASK the user before acting.

## Context you must know

- This is a rebranded fork. Real command sources are `bin/unbloarchy-*`. Every
  `bin/omarchy-*` is a GENERATED compat shim whose second line is
  `# Generated by generate-compat-shims.sh; do not edit.` They are rebuilt by
  `install/helpers/generate-compat-shims.sh` and must never be hand-merged.
- Read `AGENTS.md` at the repo root for conventions, and `../UPSTREAM-SYNC.md`
  (one level above the repo) for the overall procedure.

## Locate things

- Repo root: prefer the current directory if `git rev-parse` succeeds there;
  otherwise try `./unbloarchy`. If still ambiguous, ask the user.
- Confirm a merge is in progress (`.git/MERGE_HEAD` exists or `git status`
  shows `|merge`). If not, tell the user and stop — do not start a merge.

## Understand the merge output

- `Resolved '<path>' using previous resolution.` → rerere auto-applied a prior
  resolution and staged it. Accept it, but review significant files with
  `git diff --cached --stat`. It is NOT automatically correct.
- `CONFLICT (content): <path>` → marker edit needed.
- `CONFLICT (modify/delete): <path>` → keep-or-delete decision.
- `Recorded preimage for '<path>'` → still unresolved.

## Resolve all conflicts

Start with `git diff --name-only --diff-filter=U`. Work until it is EMPTY.
Enable base context in markers first: `git config merge.conflictstyle zdiff3`.

### Modify/delete — standard policy

DELETE (`git rm`) — from the standard set, which matches the
voxtype→dictation / menu rename direction:

- `bin/omarchy-voxtype-install`, `bin/omarchy-voxtype-status`
- `default/hypr/bindings/voxtype.lua`
- `install/user/first-run/install-voxtype.hook`
- `test/shell.d/voxtype-invitation-test.sh`
- `default/omarchy/omarchy-menu.jsonc` — BUT before deleting, diff it against
  `default/unbloarchy/unbloarchy-menu.jsonc` and ASK the user whether any new
  upstream entries should be ported into the fork's menu.

KEEP (`git add`):

- `shell/plugins/bar/indicators/Dictation.qml`
- `default/bash/fns/agent-accounts`
- `default/hypr/apps/windows-vm.lua`

Confirm the dictation / `unbloarchy-menu.jsonc` replacements exist before
deleting anything.

Any modify/delete file NOT in the standard list: ASK the user whether to keep
or delete before acting.

### Content conflicts

- Generated shims (`bin/omarchy*` carrying the generator marker): do NOT
  hand-merge, and never take `--theirs` here — that would overwrite the
  fork's wrapper with upstream's raw source. KEEP the wrapper:
  `git checkout --ours -- <file> && git add <file>`. They are regenerated
  later anyway.
- The upstream FEATURE changes in those shim conflicts belong in the fork's
  real source. For each conflicted `bin/omarchy-<name>`, port stage 3 into
  `bin/unbloarchy-<name>`:
  - `bin/unbloarchy-<name>` is a brand-normalized copy of the merge base (no
    genuine fork divergence): `git show :3:bin/omarchy-<name> >
    bin/unbloarchy-<name>`, left RAW — do not pre-rebrand; the rebrand sweep
    transforms it later.
  - It carries genuine fork changes: 3-way merge upstream's new version onto
    it by hand; ASK me when ambiguous.
  - No `bin/unbloarchy-<name>` exists at HEAD (upstream-ADDED file): ASK
    whether to `git rm` it (upstream-only, not wanted) or port it to a new
    `bin/unbloarchy-<name>` command.
- `bin/omarchy` (the router wrapper): same policy — keep ours at that path,
  port upstream's router changes to `bin/unbloarchy` (the fork's real
  router).
- Real files: edit out the `<<<<<<<` / `=======` / `>>>>>>>` blocks (use
  `zdiff3`'s `||||||| base` section to judge). For hard files prefer a 3-way
  view — fugitive (`:Gdiffsplit!`, edit the MIDDLE window) or
  `git mergetool`.

Apply these rules in priority order:

1. Keep Unbloarchy naming for anything user-facing (commands, skills, docs).
2. KEEP these literally `omarchy` — never rebrand them:
   `/usr/share/omarchy`, `/usr/share/omarchy-iso`, `/usr/share/omarchy-nvim`,
   `/usr/share/fonts/omarchy`, `/etc/omarchy.conf`, `/etc/omarchy-*.env`, the
   pacman `[omarchy]` repo section, `omarchy.org`, `omacom/omarchy`,
   `omarchyplugins`.
3. Take theirs (upstream) for genuinely new upstream-only content where the
   fork has no divergence, then let the rebrand sweep handle it later.
4. Renames (upstream `voxtype` → fork `dictation`): if the fork already
   renamed the command, mirror that with `git mv` instead of keeping both.

If a content conflict is genuinely ambiguous (real feature changes, not just
rename noise), ASK the user which way to resolve it.

### Reconcile cleanly-merged upstream files (even with UU empty)

The UU loop only sees real conflicts. Upstream ALSO modifies/adds files that
then auto-merge — they never enter the UU list and would otherwise land as
real `bin/omarchy-*` content. After the UU loop, and while a merge is still
in progress, scan EVERY tracked `bin/omarchy-*` (including `bin/omarchy`)
and for any that does NOT carry the generator marker:

- A `bin/unbloarchy-<name>` exists at HEAD → the `omarchy-*` path must be a
  SHIM again and the feature lives in `unbloarchy-*`:
  - Restore the shim: `git checkout HEAD -- bin/omarchy-<name> &&
    git add bin/omarchy-<name>`.
  - Port the feature: if `bin/unbloarchy-<name>` was a pure brand-copy of
    the merge base (no fork tweaks), overwrite it with the merged real
    content (the current `bin/omarchy-<name>` worktree version), RAW — the
    rebrand sweep rebrands it later. If it carries genuine fork changes,
    3-way merge by hand and ASK when ambiguous. `git add bin/unbloarchy-<name>`.
- No `bin/unbloarchy-<name>` exists at HEAD (upstream-ADDED command) → ASK
  the user: `git rm bin/omarchy-<name>` (not wanted) or `git mv
  bin/omarchy-<name> bin/unbloarchy-<name>` (port it; the shim is
  regenerated later, the sweep rebrands the content).
- `bin/omarchy` (the router wrapper): keep the shim sorting out the same
  way — restore `git checkout HEAD -- bin/omarchy`, port the merged router
  content to `bin/unbloarchy`, `git add` both.

Then sweep the reconcile pass for the same damage OUTSIDE bin/: upstream
ADDED files that auto-merged keep their `omarchy` filenames while their
references get rebranded — broken targets. `python3 ../sweep.py --dry` (or
`--work <repo>`) already runs a content pass; the sweep ALSO prints a
`rename-needed:` section listing tracked paths still named `omarchy` that do
not exist at HEAD. Every such path must be `git mv`'d to its `unbloarchy`
name (mirroring the resolution above and the compat list in
`test/shell.d/rebrand-integrity-check.py`) or be added to that compat list
with justification. Do not commit a merge whose sweep reports `rename-needed:`
anything.

### Final gate before reporting done

`python3 ../sweep.py --dry` must end with NO `rename-needed:` entries, and
`bash test/shell.d/rebrand-integrity-test.sh` must pass while UU stays empty.
That test fails on two things the content sweep can silently leave behind:
merge-new `omarchy`-named files, and references whose `unbloarchy` twin now
exists in the tree (renamed targets). It is part of `./test/shell`, so it also
guards every future sync commit automatically. A test failure here lists
concrete `path:line` fixes; fix them (or justify an addition to the compat
list) before the user commits.

Do NOT run the sweep, regenerate shims, commit, or push here.

### After each file

`git add <file>` (or `git rm`). When `git diff --name-only --diff-filter=U`
prints nothing, STOP and report:

- the resolution summary (what was kept/deleted);
- the remaining files staged by rerere that you reviewed;
- do NOT commit, sweep, regenerate shims, or push — those are the user's steps.
